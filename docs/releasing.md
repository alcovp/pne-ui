# Выпуск pne-ui

Публикацию запускает отправка annotated git-тега `npm/v<version>` в `origin`. Единственный workflow
[publish.yml](../.github/workflows/publish.yml) проверяет код, собирает библиотеку и публикует полученный
архив через npm Trusted Publishing / OIDC. Обычные push веток не запускают CI или публикацию; GitHub Release
и ручной запуск workflow через веб-интерфейс не нужны.

Этот процесс требует однократного подключения npm/GitHub, описанного ниже. Наличие scripts и workflow
в локальной ветке само по себе не означает, что удалённые настройки уже выполнены.

## Подготовка и отправка из терминала

Перед подготовкой зафиксируйте готовые изменения в выбранной ветке. Рабочее дерево должно быть чистым,
включая untracked-файлы; detached HEAD не допускается. RC можно готовить в feature-ветке, stable — только
в `master`. Пакетный менеджер проекта — Yarn; Node 24.14.0 задаётся в `.nvmrc`, workflow проверяет bundled npm 11.9.0.
`yarn release:check` локально выполняет сборку, все проверки и создание проверенного архива в `.release/`,
без изменения версии, git refs или npm. `yarn check` также сначала собирает библиотеку;
`yarn check:built` проверяет уже подготовленные ESM/CJS.

```bash
# Следующий RC: только локальное изменение версии, commit и tag.
yarn release:prepare --channel next --bump prerelease

# Проверить подготовленную отправку, ничего не отправляя.
yarn release:send --dry-run

# Явно отправить выбранный релиз; эта команда запускает публикацию.
yarn release:send

# Прочитать результат и ссылки из терминала.
yarn release:status
```

`release:prepare` принимает обязательный `--channel next|latest` и ровно один способ выбора версии:

| Аргументы | Назначение |
| --- | --- |
| `--bump prerelease` | Следующий RC; используется с `--channel next`. |
| `--bump patch`, `--bump minor`, `--bump major` | Выбор масштаба новой версии; `next` подготавливает RC, `latest` — стабильный номер. |
| `--version <SemVer>` | Явно заданная версия, соответствующая выбранному каналу. |
| `--version current` | Использовать номер уже зафиксированного `package.json`, без повышения и пустого коммита. |
| `--dry-run` | Показать план подготовки без изменения файлов, коммита или тега. |

`stable` принимается как alias канала `latest`. Канал `next` разрешает только форму `X.Y.Z-rc.N`;
`latest` — `X.Y.Z`. Другие prerelease-суффиксы не входят в этот процесс.

При изменении номера `prepare` создаёт отдельный коммит только для `package.json`; уже готовые изменения
не подмешиваются в version commit. Затем создаётся annotated tag `npm/v<version>` с метаданными версии,
канала, ветки и commit. В режиме `--version current` tag указывает непосредственно на текущий HEAD.
Подготовка не обращается к сети, поэтому ещё не подтверждает свободный номер в npm.

`release:send [--tag npm/v<version>] [--dry-run]` проверяет чистоту дерева, HEAD, ветку, manifest и
метаданные тега. Без `--tag` на HEAD должен находиться ровно один подходящий релизный тег. Команда проверяет
`origin` как `alcovp/pne-ui`, актуальное состояние npm и возможность fast-forward удалённой ветки.
Отсутствие ответа registry считается ошибкой отправки.

Реальная отправка — один atomic push в `origin`, содержащий ровно текущую ветку и выбранный тег.
Посторонние теги не отправляются, force push не используется. Если сервер отклоняет atomic push,
команда завершается ошибкой, не переходя к двум отдельным push. В `--dry-run` проверки читают сеть,
но команда `git push` вообще не вызывается.

`release:status [--tag npm/v<version>]` выводит JSON: локальную версию, сведения релизного тега на HEAD,
текущие npm dist-tags и ссылки на npm и GitHub Actions. GitHub CLI для него не нужен. Это чтение состояния:
refs и публикации не меняются, недоступность registry отражается предупреждением. Ссылка на GitHub ведёт
к запускам workflow; локальный статус сам по себе не является доказательством успешного CI.

## Проверки и публикация в GitHub Actions

Workflow слушает только push тегов `npm/v*`. Тег обязан соответствовать версии `package.json`.
RC публикуется с явным dist-tag `next`; stable — `latest`, причём CI отдельно проверяет принадлежность
коммита истории `master`. Подготовка тега вне локального helper не отменяет эти проверки.

Две jobs разделяют сборку и полномочия публикации:

1. **Build / check / pack:** immutable install, сборка ESM/CJS, проверки API и contracts, тесты,
   линтер и проверки stories, упаковка и проверка состава архива. Эта job не получает `id-token: write`.
2. **Publish:** получает архив из первой job текущего run, проверяет его и публикует именно этот `.tgz`
   в environment `npm-release`. Здесь выдаётся `id-token: write`; проект не пересобирается и его
   lifecycle scripts повторно не запускаются.

OIDC используется непосредственно при `npm publish`; `npm whoami` не является проверкой этого входа.
Для GitHub используется hosted runner. Доверие npm привязано к репозиторию, workflow и environment,
поэтому постоянный publishing token новой job не требуется. См. [npm Trusted Publishing](https://docs.npmjs.com/trusted-publishers/).

После сбоя не запускайте `prepare` автоматически: сначала прочитайте статус и лог имеющегося релиза.
Опубликованную npm-версию нельзя повторно выпустить с другим содержимым. Для исправленного кода готовится
новая версия; существующие релизные теги не переносятся. Обычный повторный push уже существующего тега
не создаёт новый release event. Если публикация состоялась, а следующая проверка registry упала,
повторите существующую publish job: она пропустит публикацию только при совпадении SHA-512/SHA-1
архива и текущего целевого dist-tag. Если канал уже ушёл вперёд, повтор завершится ошибкой без отката.
Проверка registry выполняется сразу после публикации; временная недоступность может потребовать
такого повторного запуска. Сам `npm publish` автоматически не повторяется.

Выпускайте по одному релизу и дождитесь результата перед отправкой следующего. Concurrency не отменяет
активный publish, но GitHub хранит только один ожидающий run: более новый может заменить предыдущий
ожидающий. Сбой или отмену перед публикацией следует разбирать по существующему тегу.

## Однократное подключение

Следующие действия изменяют удалённые настройки и выполняются отдельно, после согласования внедрения.
Эта инструкция не подтверждает, что они уже выполнены.

1. Доставить новый `publish.yml`, scripts и сопутствующие файлы в `master` и активную feature-ветку,
   из которой будет выпущен RC. Обычный push этих веток не должен выпускать пакет. Нельзя ставить
   релизный тег на старый коммит с прежним workflow.
2. Создать GitHub environment `npm-release`: разрешить подходящие **теги** `npm/v*`, не ветки;
   не задавать required reviewers и wait timer, если каждый выпуск должен завершаться без ручного
   подтверждения. Ограничение ref и approval — отдельные настройки. См. [GitHub environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments).
   Настроить tag ruleset для `npm/v*`: ограничить создание релизных тегов доверенными releasers,
   запретить обновление и удаление существующих тегов. Право выпускать такой тег даёт право публикации
   кода из выбранной ветки, поэтому это основной контроль выпуска.
3. Настроить npm trust для пакета `pne-ui`, репозитория `alcovp/pne-ui`, файла `publish.yml`
   и environment `npm-release`, явно разрешив прямую публикацию.

```bash
# Сначала проверить имеющиеся настройки; команда ничего не изменяет.
npm trust list pne-ui

# Однократное создание доверия после согласования.
npm trust github pne-ui --repo alcovp/pne-ui --file publish.yml --env npm-release --allow-publish
```

Для `npm trust` нужен npm 11.15.0+, доступ на запись к существующему пакету и включённая account 2FA.
Первое изменение доверия требует интерактивного подтверждения npm. `--allow-publish` нужен для прямого
`npm publish`: staged publishing не заменяет его и предполагает отдельное подтверждение выпуска.
Существующую конфигурацию сначала следует прочитать, а не удалять автоматически.
См. [npm trust CLI](https://docs.npmjs.com/cli/v11/commands/npm-trust/).

4. После согласованной настройки отключить старые удалённые workflows Chromatic и диагностический
   `publish-next.yml`; его копия может оставаться в старой ветке, даже если файла уже нет в `master`.
   Удаление диагностических веток — отдельная согласованная уборка. История запусков не мешает новому
   процессу. Существующий environment `github-pages` не относится к этой замене и сохраняется.
5. Выполнить первый отдельно согласованный RC-релиз через `prepare` / `send`, проверить успешный OIDC run,
   версию, целевой dist-tag и архив npm. До этой проверки сохранить имеющийся GitHub secret `NPM_TOKEN`;
   новый workflow его не использует. Удалять устаревший секрет следует только после подтверждённого
   перехода на OIDC.

## Локальная разработка

`yarn storybook` и `yarn build-storybook` продолжают работать без Chromatic. Stories и документация
компонентов сохранены; удалён только сервис публикации визуальных snapshot и его addon.
Сборка, проверки и публикация теперь вызываются явно: старые составные aliases, одновременно
повышавшие номер и делавшие `npm publish`, не являются интерфейсом релиза.
